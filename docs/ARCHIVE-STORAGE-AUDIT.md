# Archive storage audit — making GitHub lightweight

Status: Pass-1 (current-tree removal). Pass-2 (git history rewrite) is **not**
performed here — see the closing section.

## Goal

Keep the repository verifiable while making the GitHub source download light.
GitHub becomes the source, build recipe, current public tree and **verification
record**; the live server (`https://trentpower.fr/integrity/releases/`) is the
canonical store for the heavy historical edition **archive binaries**.

## What was heavy

Measured on `origin/main` (`2d401c5`):

| Thing | Size |
|---|---|
| `.git` (full history pack) | ~3.1 GiB |
| Working tree | ~3.6 GiB |
| Tracked archive binaries in current tree | **54 files, ~289 MB** |
| `public/integrity/releases/` total | ~292 MB (≈3 MB after removal) |

The 54 binaries are `trentpower-fr-<edition>.zip` and `.tar.gz` under
`public/integrity/releases/<edition>/`. Git history additionally carries every
**daily rebuild** of those archives (`git rev-list` shows the same ~8 MB blobs
recommitted across many build-days) — that is the bulk of the 3.1 GiB pack.

## What moves, what stays

**Removed from the current tree (server-canonical):** the `.zip` / `.tar.gz`
binaries only.

**Kept in git for every edition (the verification record):**
`*.zip.sha256`, `*.tar.gz.sha256`, all `*.sig`, `SHA256SUMS(.sig)`,
`integrity-redistributable.json(.sig)`, `release.json(.sig)`, `builds.json(.sig)`,
`EXCLUDED_FILES.*`, `TESTRESULTS.txt(.sig)`, per-edition `index.html`.

Because each archive's committed `.sha256` (and its `.sig`) stays in git, a
server-downloaded archive can be verified against a hash that was committed and
signed here — no need to trust the server.

## Safety verification (done before any removal)

- `integrity.json` hashes **zero** archive binaries (confirmed: no
  `.zip`/`.tar.gz` references). Removing them does not break the signed
  integrity manifest.
- All **54** binaries were confirmed present on the live server (HTTP 200, real
  byte sizes) before `git rm`. The canonical copy already exists.
- Deploy mirror is lftp `mirror -R` with **no `--delete`**
  (`docs/BUILD-AND-DEPLOYMENT.md`), and it mirrors the **filesystem**, not git.
  So: (a) removing binaries from git cannot delete the server copies; (b) a
  release build still writes the binaries to `public/` on disk and the mirror
  uploads them — they simply never get committed (now `.gitignore`d).

## Coupled systems that had to be taught "binary-absent" (the non-obvious part)

The brief assumed a simple delete. In reality three trust-surface systems
referenced the binaries:

1. **`frozen_archives_immutable` gate** (`tools/quality/inline_checks.py`) hashed
   `<basename>.zip` / `.tar.gz` against `metadata/archive-baseline.json`. Fixed:
   dropped the two binary lines from the `byte_stable` list (kept the `.sha256`
   lines) and pruned the 14 binary keys from `archive-baseline.json`. The
   committed checksum is now the editorial seal; the bytes are verified remotely.
2. **`validate_release.py` Step R2** (`tools/verify/`) *opened* the canonical
   `.zip` and checked its contents. Fixed: when no local archive is present it
   confirms the committed `.sha256` seal exists and reports archive↔manifest byte
   verification as an explicit **remote** step instead of failing.
3. **Public-exposure / allow-list / source-mirror** machinery. The two new
   pointer files are new public files, so: `index.json` got a serve rule
   (`tools/lib/htaccess_config.py` + `PUBLIC_INTEGRITY_GLOBS`); `README.md`
   (`.md`, security-denied extension, already in the deploy `*.md` exclude) was
   added to `DEPLOY_EXCLUDED_GLOBS`; both were added to
   `source-mirror-exclusions.json`. The server keeps its existing
   `trentpower-fr-*.zip` allow rules — it still serves the binaries it holds.

## Local build does NOT need the historical binaries

`bash tools/build/build.sh --check` never reads or requires them (it exits
before the archive stage). `gate.py` no longer fails on their absence. Only an
explicit remote verification needs the server bytes.

## Architectural note — why this is a build-converged change, not a hand-edit

This repository commits a **fully-built** public tree whose hashes interlock
(`integrity.json` ↔ `/source/` mirrors ↔ `page_provenance` ↔ `sri_coherence` ↔
verification map). Changing the public file set (removing 54 binaries, adding 2
pointers) and the generated configs (`.htaccess`, `public-exposure.json`) ripples
through that graph. The derived tree therefore must be regenerated by the normal
`build.sh` convergence (with licensed fonts present) and `integrity.json`
re-signed — it cannot be coherently assembled by editing individual files. The
**source** change in this patch is minimal and self-contained; the derived
artefacts are a build product.

## Guardrails added

- `.gitignore`: `public/integrity/releases/**/*.{zip,tar.gz,tgz,tar,7z,br}` so a
  release build's on-disk binaries are never recommitted (sidecars unaffected —
  they end in `.sha256`/`.sig`, not the archive extensions).
- `public/integrity/releases/README.md` + `index.json`: lightweight pointers to
  the canonical server store.
- `validate_archive_storage_policy.py` — a blocking gate (wired into the check
  registry) that fails if any archive binary is committed under
  `public/integrity/releases/`, with a unit-test suite covering the allowed
  sidecars and the forbidden binary extensions.

## Pass-2 (history rewrite) — deliberately NOT done

Removing the binaries from the current tree makes the **GitHub source ZIP** and
future shallow clones light immediately. It does **not** shrink full
`git clone` history — the ~3 GiB of historical archive blobs remain until a
`git filter-repo` rewrite. That rewrite is out of scope here because it
conflicts with this repo's own rules (`NEVER force-push main`, ruleset
`protect-main` no-bypass, `require_signatures`) and must be a deliberate,
backed-up, supervised event. Decide it separately.
